## 0. Архитектурная философия

За 6 часов выигрывает не сложность, а **предсказуемость**. Каждое архитектурное решение ниже подчинено трём принципам:

1. **Один процесс, один порт с каждой стороны.** Никакого Docker, никаких очередей (Celery/Redis), никакой асинхронной обработки в фоне — LLM-вызов делаем синхронно прямо в хендлере `ingest`. Для демо на 5-10 тикетов это не проблема, а нам не нужен воркер.
2. **LLM — единственный "мозг", всё остальное — детерминированный код.** Декомпозиция, категоризация и черновик ответа — это одна LLM-функция со строгим JSON-контрактом. Роутинг (AUTO_REPLY vs тикет), сортировка по колонкам, приоритеты отображения — чистый Python/TS, без повторных обращений к модели.
3. **SQLite = файл `app.db`.** Не поднимаем Postgres. Одна таблица `tickets` покрывает весь MVP.

## 1. Стек технологий

| Слой | Технология | Почему |
|---|---|---|
| Backend | **FastAPI** + Uvicorn | Автогенерация OpenAPI/Swagger, нативная валидация через Pydantic — жюри можно показать `/docs` вживую |
| Валидация/схемы | **Pydantic v2** | Тот же класс используется и как контракт для LLM, и как модель API-ответа |
| БД | **SQLite** через **SQLModel** | SQLModel = Pydantic + SQLAlchemy в одном классе, минимум boilerplate |
| LLM-вызов | **Anthropic Claude API** (`claude-sonnet-4-6`) через structured output / tool-use, с абстракцией-клиентом | Если на хакатоне есть доступ к GigaChat API (свой продукт СберТеха) — это может дать бонус у жюри; закладываем `llm_client.py` с одной функцией `decompose(text) -> DecompositionResult`, чтобы провайдера можно было заменить за 10 минут без изменения остального кода |
| Фронтенд | Лежит в supportpilot-react | Дополни его | 
| Drag & Drop | **@dnd-kit/core** | Канбан с перетаскиванием карточек между колонками за 1 компонент |
| Иконки | **lucide-react** | Уже есть в экосистеме shadcn, значок ⚠️ — просто `<AlertTriangle />` |

**Запуск в 2 команды** (без Docker):
```
# Терминал 1
cd backend && pip install -r requirements.txt && uvicorn main:app --reload --port 8000

# Терминал 2
cd frontend && npm install && npm run dev
```
CORS открываем на `*` для локального демо (`allow_origins=["*"]` в FastAPI middleware) — на MVP это осознанный компромисс, не тратим время на прод-настройку.

## 2. JSON-схема для LLM (ядро системы)

LLM вызывается **один раз на входящее сообщение** и обязана вернуть строго валидный JSON по этой схеме (задаём через structured output / response format, не через "попроси вежливо в промпте").

### 2.1. Перечисления

```python
class Category(str, Enum):
    WIFI = "wifi"
    VPN = "vpn"
    ACCESS_CONTROL = "access_control"      # СКУД / пропуска
    PERSONAL_CABINET = "personal_cabinet"  # Личный кабинет сотрудника
    PASSWORD_RESET = "password_reset"
    HR = "hr"                              # отпуска, кадровые вопросы
    OTHER = "other"

class Priority(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"
    URGENT = "urgent"

class ActionType(str, Enum):
    AUTO_REPLY = "auto_reply"                      # есть в базе знаний, можно ответить сразу
    CREATE_TICKET = "create_ticket"                 # нужен оператор, но контекста достаточно
    REQUEST_CLARIFICATION = "request_clarification" # не хватает данных для решения
    ESCALATE = "escalate"                           # срочно, требует человека вне очереди
```

### 2.2. Схема одной подзадачи (sub-ticket)

```python
class SubTicket(BaseModel):
    original_fragment: str          # дословная цитата из письма, породившая тикет
    summary: str                    # краткая суть проблемы (1 предложение)
    category: Category
    priority: Priority
    action_type: ActionType
    requires_clarification: bool
    missing_info: list[str] = []    # что именно нужно уточнить у пользователя, если requires_clarification=true
    kb_template_id: str | None      # id шаблона из базы знаний, если category покрыта KB
    draft_reply: str | None         # готовый черновик ответа (генерируется LLM на основе KB-шаблона либо с нуля)
```

### 2.3. Схема ответа LLM на всё сообщение

```python
class DecompositionResult(BaseModel):
    source_text: str
    tickets: list[SubTicket]
```

### 2.4. Пример входа/выхода (для промпта и для демо жюри)

## 4. Модель данных (таблица `tickets`)

Одна таблица — источник истины и для API, и для Канбана.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int, PK | автоинкремент |
| `parent_message_id` | str (UUID) | группирует sub-tickets, пришедшие из одного письма |
| `original_fragment` | text | цитата из исходного текста |
| `summary` | text | краткое описание |
| `category` | str (enum) | см. п. 2.1 |
| `priority` | str (enum) | Low/Medium/High/Urgent |
| `action_type` | str (enum) | см. п. 2.1 |
| `requires_clarification` | bool | |
| `missing_info` | json (list[str]) | |
| `kb_template_id` | str, nullable | |
| `draft_reply` | text, nullable | редактируемый черновик, можно PATCH-ить оператором |
| `status` | str (enum: `new`, `in_progress`, `resolved`) | колонка Канбана |
| `created_at` | datetime | |
| `updated_at` | datetime | |

`status = new` выставляется по умолчанию для всех тикетов с `action_type = create_ticket / request_clarification / escalate`. Тикеты с `action_type = auto_reply` **тоже создаются в таблице** (для аудита), но сразу помечаются `status = resolved` — это и даёт красивый демо-эффект "мгновенного авто-ответа" в колонке "Решённые".

## 5. REST API

### `POST /api/tickets/ingest`
Приём сырого текста → вызов LLM → сохранение подзадач.

**Request:**
```json
{ "raw_text": "Не могу подключиться к Wi-Fi...", "allow_ai_reply": true }
```
**Логика:**
1. Вызов `llm_client.decompose(raw_text)` → `DecompositionResult`.
2. Для каждого `SubTicket`:
   - если `action_type == AUTO_REPLY` и `allow_ai_reply == true` → сохранить со `status = resolved`;
   - если `allow_ai_reply == false`, даже AUTO_REPLY-кандидаты понижаются до `CREATE_TICKET` со `status = new` (пользователь не разрешил автоответ) — это по ТЗ ("если пользователь разрешил ИИ-ответ");
   - иначе → `status = new`.
3. Массовая запись в SQLite, генерация общего `parent_message_id`.

**Response `201`:**
```json
{ "parent_message_id": "uuid", "created_tickets": [ /* массив тикетов с id */ ] }
```

### `GET /api/tickets`
Список для Канбана.

**Query-параметры:** `status` (`new|in_progress|resolved`, опционально), `priority` (опционально), `category` (опционально).

**Response `200`:** массив тикетов, отсортированный так, чтобы `priority = urgent` всегда были первыми внутри своей колонки (сортировка на бэкенде, чтобы фронт не думал).

### `PATCH /api/tickets/{id}`
Смена статуса и/или редактирование ответа оператором.

**Request (частичное обновление):**
```json
{ "status": "in_progress", "draft_reply": "отредактированный оператором текст" }
```
**Response `200`:** обновлённый объект тикета.

### Дополнительно (не по ТЗ, но 5 минут работы и сильно улучшает демо)
`POST /api/tickets/{id}/send` — фиктивная "отправка" ответа (просто переводит `status → resolved` и ставит `sent_at`), под кнопку "Применить/Отправить" в карточке.

## 6. Дизайн Канбана и демо-сценарий

### 6.1. Экран
- Тёмная тема (`bg-zinc-950`, карточки `bg-zinc-900`, акценты через `Tailwind` — Urgent красный, High оранжевый, Medium жёлтый, Low серый).
- Три колонки: **Новые** / **В работе** / **Решённые**, счётчик тикетов в заголовке колонки.
- В колонке "Новые" тикеты с `priority = urgent` закреплены сверху и помечены значком ⚠️ (лёгкая пульсация/подсветка рамки — дешёвый, но эффектный CSS-трюк).
- Карточка в списке: `summary`, бейдж категории, бейдж приоритета, миниатюра исходного фрагмента (1 строка с обрезкой).
- Клик по карточке → модалка/side-panel (shadcn `Dialog`/`Sheet`):
  - исходный фрагмент текста целиком,
  - `missing_info` списком, если `requires_clarification = true`,
  - редактируемое поле `draft_reply` (textarea, предзаполненная),
  - кнопка **"Применить/Отправить"** → вызывает `POST /api/tickets/{id}/send`.
- Drag & drop карточек между колонками → `PATCH /api/tickets/{id}` со сменой `status`.

### 6.2. Демо-сценарий (2-3 минуты защиты)
1. Открыть форму ввода, вставить составное сообщение (Wi-Fi + отпуск, пример из п.2.4). Отметить чекбокс "Разрешить ИИ отвечать автоматически".
2. Нажать "Отправить" → показать, как за секунды из одного сообщения родились два тикета: один сразу улетел в "Решённые" (авто-ответ по Wi-Fi), второй появился в "Новые" с пометкой "нужны уточнения" (отпуск).
3. Заранее (до демо) заготовить в БД ещё 2-3 тикета, среди них один `urgent` (например, "СКУД заблокировал пропуск, стою у двери") — показать значок ⚠️ и то, что он автоматически наверху колонки.
4. Открыть карточку срочного тикета → показать черновик ответа, отредактировать одно слово, нажать "Применить/Отправить" → карточка визуально уезжает в "Решённые".
5. Показать `/docs` (Swagger) как бонус — "весь бэкенд самодокументируется".

## 8. Риски и точки упрощения, если не укладываетесь по времени

- **Нет времени на drag&drop** → оставить смену статуса только кнопками ("Взять в работу" / "Решено") внутри карточки, без `@dnd-kit`.
- **LLM иногда возвращает невалидный JSON** → заложить в промпт жёсткое "ответь ТОЛЬКО JSON, без markdown-разметки" и один retry; как fallback — если парсинг не удался дважды, создать один тикет `category=other, action_type=create_ticket` с полным текстом письма, чтобы демо не падало.
- **Нет доступа к нужному LLM-провайдеру в моменте** → `llm_client.py` спроектирован как единственная точка замены провайдера, переключение — это правка одной функции, а не архитектуры.
